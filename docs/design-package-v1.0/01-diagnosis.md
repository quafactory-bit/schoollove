# SchoolLoveI Product Diagnosis v1.0

Status: **FROZEN**

## 0. 목적

이 문서는 기존 SchoolLoveI를 버리지 않고, 왜 리팩터링이 필요한지와 v1.0에서 무엇을 바로잡는지를 정의한다.

---

## 1. 현재 제품의 핵심 문제

기존 구현에는 검색, 학교 페이지, 기수·반 페이지, 등록, 관리자, SEO가 이미 존재한다.

문제는 기능 부족이 아니라 **사용자 경험의 중심이 분산되어 있다는 것**이다.

### 문제 A — 학교 검색이 제품처럼 보인다

사용자는 학교를 검색하지만 실제로 원하는 것은 사람이다.

검색과 학교 페이지가 전면에 오면 제품이 "학교 정보 서비스"처럼 보인다.

### 문제 B — School → Year → Class가 페이지 나열처럼 보인다

사용자는 같은 사람 목록을 좁히고 있는데, 화면은 서로 다른 페이지를 이동하는 느낌을 준다.

### 문제 C — 등록이 입력 폼처럼 보인다

등록은 학교 성장의 핵심 행동인데, 기존 흐름에서는 필드 입력 작업으로 인식되기 쉽다.

### 문제 D — 학교의 성장이 체감되지 않는다

등록 수가 늘어도 사용자가 "우리 학교가 살아 있다"고 느끼는 구조가 약하다.

### 문제 E — Home이 목적을 설명하지 못한다

기존 Home의 검색·인기 학교·최근 등록 묶음은 기능 진입점은 제공하지만 SchoolLoveI의 성장 감각을 지속적으로 보여주지 못한다.

## 2. 진단에 따른 제품 전환

| 기존 인식 | v1.0 전환 |
|---|---|
| 학교 검색 서비스 | 사람 발견 서비스 |
| 페이지 이동 | 사람 목록 필터링 |
| 등록 폼 | 학교 성장 기여 |
| 레벨 숫자 | 성장 진행감 |
| 최근 등록 목록 | 학교 성장 순간 Feed |
| 개인 프로필 목적지 | Instagram으로 나가는 Profile Card |

## 3. P1 우선순위

1. Product Principles 고정
2. Level Policy 계약 고정
3. Home Feed를 성장 순간 피드로 전환
4. School Hub State A/B/C/D 적용
5. Year/Class/Profile을 People Discovery 흐름으로 재구성
6. Register Flow를 Growth Engine으로 연결
7. Search를 발견 진입점으로 정리
8. Admin을 신뢰 유지 시스템으로 정리
9. SEO 경계와 URL 계층 고정
10. DB/API를 기존 구조 재사용 기준으로 정리

---

## 4. 기존 자산 재사용 원칙

v1.0은 기존 다섯 핵심 테이블을 중심으로 한다.

- `schools`
- `profiles`
- `search_logs`
- `traces`
- `reports`

새로운 제품 철학을 위해 새 DB를 만드는 방식은 사용하지 않는다.

P1 DB 변경은 `12-db-schema.md`에 명시한 **3개 컬럼 추가**로 제한한다.

---

## 5. 성공 기준

리팩터링 후 사용자가 다음 흐름을 자연스럽게 느껴야 한다.

> 찾는다 → 발견한다 → 등록한다 → 성장시킨다 → 다시 찾는다

사용자가 화면 이름이나 시스템 구조를 이해할 필요는 없다.

사용자는 단지 학교 이름으로 들어와 사람을 발견하고, 자신의 등록이 학교를 움직였다고 느끼면 된다.

---

## 6. 금지

- 진단을 이유로 새 기능을 무제한 추가하지 않는다.
- 새 소셜 기능을 만들지 않는다.
- 새 회원 시스템을 P1에 넣지 않는다.
- Design Package 밖의 제품 철학을 Claude Code가 임의로 만들지 않는다.
- P2/Future 항목을 P1 구현에 섞지 않는다.
